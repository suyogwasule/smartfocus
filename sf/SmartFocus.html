Phase 01 — Discover

Distraction isn't a willpower problem. It's a design problem.

Most people who lose a study session to their phone or a new tab already wanted to focus — the failure happens in the first ten minutes, in one reflexive switch, long before willpower is even the issue. Most blockers on the market treat this as a binary: a site is either allowed or not. That solves the browsing problem. It does nothing for the moment right before the switch, and it's trivially disabled the instant it creates real friction.

I didn't start from a feature list. I started by pointing a tracker at my own browser for a week and reading the pattern, not the anecdote.

Live output from the extension's own tracking module — the same signal that shaped the problem statement.

What the data actually showed: time wasn't evenly lost across the day — it clustered right after a tab switch, and the sites at the top of the list weren't obviously "bad." They were legitimate tools (a chat assistant, a classroom portal) that had simply become the path of least resistance the moment focus wavered.

That reframed the problem. The tool didn't need to be a better blacklist. It needed to make the choice point — the moment right before switching — visible and slightly more expensive, and it needed to make the pattern legible afterward so a person could actually see it happening to them.

Job to be done

"When I sit down to study or do focused work, I want something that makes distraction slightly harder and progress visible, so I don't quietly abandon the session in the first ten minutes."

Phase 02 — Define

Three jobs, not thirteen features.

Rather than scope a feature list first, I defined three product pillars every requirement had to serve. If a proposed feature didn't sharpen one of these three, it didn't make the cut — regardless of how easy it would have been to build.

Pillar 01

Control

Make distraction cost something in the moment — a timed session and a block list that's actually hard to route around mid-session.

Pillar 02

Awareness

Make the pattern visible after the fact — where time actually went, not where a person assumes it went.

Pillar 03

Accountability

Make it social when solo willpower runs out — a shared session that starts for everyone at once, not just a reminder.

Primary user — the self-motivated procrastinator

Wants to focus, opens Instagram out of habit anyway. Doesn't need to be forced into a session — needs a small, honest amount of friction and a mirror held up afterward. A parental-control-style lock would be the wrong tool for this person; it solves for someone who doesn't want to focus at all.

Phase 03 — Develop

Every build decision was a trade-off. Here are the ones that mattered.

Build order followed the same logic as the requirements: Control shipped before Awareness, and Awareness shipped before Accountability — because a session that isn't trustworthy makes the dashboard built on top of it meaningless, and a dashboard nobody trusts makes a shared group session meaningless too. Reach and confidence were highest at the core; effort and risk climbed the further out we went, which is exactly the order a RICE pass on the three pillars would predict.

Decision 01

How to handle real-time sync for group sessions?

Decided

Integrated Firebase Realtime Database to enable multi-user collaboration and true cross-device real-time sync.

Trade-off

Introduces an external dependency, but it is essential for the accountability mechanism where one user leaving impacts all participants.

Decision 02

How strict should Hard Mode actually be?

Decided

Once Hard Mode is on, pause, stop, and block-list edits lock for the session's duration.

Trade-off

Drew the line at making quitting effortful, not impossible. Locking the browser itself would trade trust for control — this is a tool people choose to open, not one forced on them.

Decision 03

Where should the blocking actually happen?

Decided

Used Manifest V3's declarativeNetRequest rules engine instead of intercepting requests in the page itself.

Trade-off

Traded some runtime flexibility — can't inspect page content before deciding to block — for reliability and Chrome Web Store compliance. A constraint the platform sets, not a preference.

Decision 04

Buy a charting library, or build it?

Decided

Hand-rolled the dashboard's charts on Canvas instead of pulling in a library.

Trade-off

Cost extra build time upfront. Paid back in a popup that opens instantly — extension popups are latency-sensitive in a way a browser dashboard tab isn't.

Phase 04 — Deliver

What shipped, and how I'd know it's working.

All three pillars shipped as scoped: a session engine with real blocking, a dashboard that turns tracking into a legible pattern, and a group mode that enforces a shared start time instead of relying on a reminder. I owned product direction and the core session engine; the wider build was a small team effort split across the analytics and group-session surfaces.

There's no live user base yet to report real numbers against, so here's the measurement plan I'd run if this shipped past our own group — built on HEART, using signals the product already tracks.

After the build

What leading this actually taught me

The biggest shift wasn't a feature decision — it was integrating Firebase Realtime Database to power the group study module. Handling real-time state synchronization and accountability disruptions across multiple users proved to be the core challenge that defined the product's architecture.

The thing I'd build differently next isn't on the feature list at all. It's retention. A tool someone opens once because it's clever isn't the same as one they open every Tuesday because it's a habit — and that's a product problem, not an engineering one.

— Suyog
